# 阿里云 AI Agent Handbook：总结与架构对照

> 阅读日期：2026-09-29；源仓库提交：`1f34b541468ba059ef1732bd1bb64940c4812936`。
> 项目基线：v1.9（本地与远端一致）；本次输出：v1.10 设计增量，不代表运行时实现。
> 阅读范围：README 全书导航；重点阅读第 4、5 章及第 19、21、23 章相关段落。其他章节仅按目录了解主题，未逐章完整核验；不引用调研统计或案例收益数字。

## 1. 核心总结

手册按照架构、构建、运行、治理和调优组织企业 Agent 生命周期。核心是把模型的一次输出纳入可控制的任务过程：模型提出行动，Harness（执行支撑系统）管理状态、上下文、工具和反馈，业务验收决定是否完成。

- **任务与消息分开**：Task 表示持续目标；Session 表示交互；Call 表示一次请求。等待审批、等待事件、取消和验证均应有明确状态（第 4 章）。
- **Context 是每轮编译结果**：先做身份和权限筛选，再处理相关性、可信度和预算，生成可解释的输入清单 Context Manifest。大型输出保存在工作区，通过引用按需读取（第 5 章）。
- **业务事实与任务事实分开**：Context 中的设备状态不能替代 Task 中的审批进度；Event Log、Snapshot、Checkpoint 分别承担事件历史、聚合视图和安全恢复点（第 5 章）。
- **完成需要证据**：工具已接受请求、模型输出结束、交付物形成和业务目标实现是不同事件；由验收器核验结果（第 4 章）。
- **轨迹是优化材料**：Trace、Session、Trajectory 不是同义词；异步和多轮任务需要可靠身份关联，记录覆盖不足时不能假装已经复原全任务（第 19 章）。
- **黄金集需要业务判据**：失败案例经过复核也可成为黄金样本；优化用题和独立检查用题分开，比较期间冻结题库（第 21 章）。
- **经验逐级固化**：先核对来源轨迹，再把稳定方法形成 Skill、SQL、Script 或 Workflow；重复提交类故障应修恢复机制，而非只改 Prompt（第 23 章）。

## 2. 对本项目的判断

既有 Wiki/Ontology/Context 分层、固化审批、动态降级和适用域声明可保留。缺口在于“谁负责推进任务、怎样知道完成、恢复时读什么、如何证明一次优化有效”。

| 优先级 | 现有缺口 | 本次设计落点 | 验证场景 |
|---|---|---|---|
| P0 | 图状态不足以表达长任务 | §3.3 TaskRun 与完成证据 | 模型自称完成但证据缺失 |
| P0 | ContextPack 没有输入解释清单 | §3.3 Manifest 与大结果引用 | 跨租户候选在排序前被拒绝 |
| P0 | 恢复后动作结果可能未知 | §3.3 动作契约与恢复顺序 | 工单已写入、本地超时，恢复先对账 |
| P1 | 黄金集未区分调优与独立验证 | §3.3 轨迹与实验闭环 | 正常例及失败例均回归 |
| P1 | Lesson 自动写入缺少候选阶段 | §3.3 经验发布 | 未验证经验不进入正式召回 |

这些是本项目的设计推导，不是手册已经实现本项目能力的证明。

## 3. 取舍与分期

采用最低充分架构：先保留一个执行主体与现有八层职责，在编排层补 TaskRun、在 ContextPack 组装器补 Manifest、在接入层补 Action 契约。新建通用多 Agent 平台、替换 LangGraph、引入完整云产品栈均暂缓。优点是验证范围小；代价是队列扩容、跨节点调度仍需后续实施。

MVP 以持久化任务记录、一次中断恢复演练、一次输入清单回放和固定数据集对照为验收。多 Agent 只在独立子任务确有隔离或并行收益时引入。
