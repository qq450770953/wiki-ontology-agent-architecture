实施路线图：从传统 RAG 演进至 Wiki-Ontology 认知架构

1. 架构演进的战略背景与目标定位

在企业 AI 战略进入深水区的当下，从“文档检索”向“知识行动”转型已不再是选项，而是必然。传统检索增强生成（RAG）本质上是基于概率的文本匹配，难以承载高确定性的决策任务。企业需要的是一种能够理解业务逻辑、精准调用工具、并具备状态感知能力的认知架构。这种转型不仅是为了消除幻觉，更是为了通过“定义世界”来建立决策的确定性，从而在根本上提升执行效率。

对比传统 RAG 与 Wiki-Ontology 架构，其核心差异决定了企业的竞争格局：

* 工具绑定与参数映射：传统 RAG 依赖 LLM 的即兴推理，常在复杂参数绑定中失效；Wiki-Ontology 通过本体约束实现确定性的参数映射。
* 参数化控制与幻觉遏制：前者依赖 Context 窗口的软约束，后者通过 Ontology（本体论）强制执行业务逻辑规则，从源头阻断非法逻辑。
* 资源利用与效能比：Wiki-Ontology 能够实现“知识复利”，通过固化高频轨迹，帮助企业跳出“Token 燃烧”的 RAG 陷阱，实现低成本、秒级响应。

本路线图遵循“记忆 (Wiki) -> 语义 (Ontology) -> 状态 (Context) -> 编排 (Workflow)”的设计哲学。这一演进过程将离散的经验转化为确定性的企业资产，引导架构进入真正的认知闭环。

2. 阶段一：构建语义底座与本体定义 (Ontology Foundation)

Ontology（本体论）是整个架构的灵魂，它承担着“定义世界”的职责。在多系统协作的复杂环境下，本体论为 Agent 提供了统一的业务语义协议，解决了不同数据源之间的语义偏移。通过构建语义底座，我们能有效降低 Agent 在多轮编排中的状态空间熵值（State-space Entropy）。

构建语义层的核心任务列表：

* [ ] 底座初始化：使用 ontology-enterprise 工具完成语义底座初始化（执行 python3 scripts/ontology_enterprise.py --root ./ontology init），建立具备 RBAC 与审计能力的本地图谱。
* [ ] 实体定义与血缘追踪：识别核心业务实体（客户、产品、订单），并建立实体来源血缘（Lineage），确保数据的可追溯性。
* [ ] 关系映射与基数约束：定义实体间的逻辑连接（如“一个合同对应一个签署主体”），利用本体约束进行环检测，防止推理自旋。
* [ ] 指标口径标准化：将业务计算逻辑（Method）写入本体，确保 Agent 调用的是经过共识的确定性计算，而非 LLM 的数值猜测。

统一的业务语言将原本复杂的推理成本转移至底座定义阶段。当世界被“定义”清楚后，后续 Agent 的决策将从“盲目搜索”转变为“语义导航”，大幅减少推理环节的计算开销。

3. 阶段二：部署六步执行管线与上下文物化 (Pipeline & Context)

当用户请求未命中已有的固化流程时，系统需启动高柔性的动态执行管线。此阶段的核心在于“上下文物化”，即通过 Context 重建世界的当前状态，确保 Agent 的决策基于最新事实。

六步执行管线详解：

步骤	动作内容	战略影响 (So What)
1. 关键词映射	提取请求核心词并映射至语义空间	缩小候选工具集，提高初步定位的命中率。
2. 实体消歧	基于 Ontology 校验实体的唯一性与真实性	预防因语义偏移导致的下游工具调用失败（Tool-call Failure）。
3. 工具映射与参数绑定	根据本体约束进行 API 匹配与强类型绑定	确保行动指令符合系统接口的硬性规范。
4. 跨系统执行	通过接入层访问真实业务系统获取实时数据	实现从“文本生成”到“业务触达”的跨越。
5. 上下文物化	将执行结论与状态写入 Context 状态机	防止 Agent 基于过期快照（Stale Snapshots）进行二次决策。
6. 汇总解释	结合 Context 与执行结果进行逻辑归因	提升决策透明度，为后续“认知回流”提供素材。

Context 层利用状态机（State Machine）与物化校验方法（Materialization Method），在长对话中持续重建世界状态。这解决了 Agent 在复杂任务中因记忆遗忘而导致的逻辑断层问题。

4. 阶段三：Workflow 固化编排与人工审批机制 (Solidification & Governance)

将“偶然的成功轨迹”转化为“必然的固化资产”是实现知识复利的关键。这一过程被称为知识编译（Knowledge Compilation），它将模糊的 LLM 推理路径编译为确定性的、基于图的执行流。

从轨迹到固化的编译逻辑：

* 执行轨迹编译：系统提取成功的六步管线记录，自动生成 LangGraph Workflow 定义。
* Wiki 层存储结构：在 Wiki 层建立固化流程注册表，存储 SQL 模板、映射表（Mapping Tables） 以及已审批的 Workflow 目录。
* 审批护栏：引入人工审批（Human-in-the-loop）机制。未过审不写 Wiki，只有通过验证的轨迹才能更新固化流程注册表，确保企业资产的纯净度。

一旦流程固化，同类问题将触发“命中优先”路径。Agent 直接加载已编译的图执行，无需重新推理。这不仅将响应耗时压低至秒级，更从根本上消除了 Token 的无效损耗。

5. 阶段四：实现认知闭环与知识复利 (Cognitive Loop & Lesson)

企业知识库应通过“知识闭环（绿色路径）”与“认知闭环（紫色路径）”实现自我进化。通过将结论与归因反馈至 Context，Agent 能够始终基于最新的现实进行推理。

经验沉淀 (Lesson) 机制的操作策略：

* 正向经验沉淀：通过 Session Memory Protocol（会话记忆协议） 记录成功任务的上下文标准，作为未来类似任务的加速参考。
* 负向经验 (Negative Knowledge) 复用：提炼执行失败的教训（如参数冲突、环境异常），并强制在同类任务开始前加载，形成“避坑指南”。
* Wiki 与 Lesson 的互补关系：Wiki 存储静态结论（编译后的确定性知识），而 Lesson 存储动态经验（发生的事实与教训），二者共同构成企业的长期记忆。

通过认知回流，执行后的新状态将实时物化到 Context 层。这种闭环确保了即使在流程已经固化的场景下，Agent 依然能感知外部世界的微小变化，维持逻辑推理与现实的一致性。

6. 全程治理、安全护栏与落地建议

在知识行动架构中，治理层是贯穿始终的横切关注点。它确保了从语义定义到执行反馈的全过程均受控于预设的安全边界。

核心治理护栏：

* 权限控制 (RBAC)：基于 Ontology 实体与 API 角色定义，限制 Agent 的资源触达边界。
* 血缘追踪 (Lineage)：记录数据从源头到决策结论的完整链条，实现执行过程的可审计。
* 确定性校验 (Determinism Checks)：在 Workflow 编排层通过 Method 进行计算校验，防止逻辑偏移。
* 失效机制：对 Wiki 中的 SQL 模板与规则设置有效期，过期资产自动触发重新校验流程。

落地自查清单 (Checklist)：

* [ ] 语义初始化：是否已执行 ontology-enterprise 初始化脚本并建立基础 Object/Link？
* [ ] 约束定义：核心业务实体的基数约束与环检测逻辑是否已在本体层配置？
* [ ] 双路径跑通：是否实现了“命中优先”与“六步执行”的自动路由切换？
* [ ] 编译审批流程：从执行轨迹到 LangGraph Workflow 的自动生成与人工审批链路是否闭合？
* [ ] 状态物化校验：Context 层是否能实时拦截并更新基于过期快照的决策指令？

结语 Wiki-Ontology 架构标志着企业 AI 从“生成式”向“认知式”的跨越。通过构建本体底座、物化上下文状态、并不断固化成功路径，企业将构建起一个具备高确定性与自我进化能力的数字大脑，最终实现从昂贵的重复推理到持续积累的知识复利飞跃。
