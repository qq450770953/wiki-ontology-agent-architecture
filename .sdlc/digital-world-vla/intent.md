# Intent: 数字世界 VLA Agent 架构拓展
Author: 用户 / AI 架构协作。Status: accepted (2026-10-21).

## Problem
当前项目已经定义了 Wiki、Ontology、Context、Workflow、Connector Runtime 和治理闭环，但这些能力仍主要以企业知识行动架构的概念组织，尚未明确形成一个面向数字世界的 VLA（Vision-Language-Action）Agent 架构。

项目缺少一套统一的资产与运行边界，使 Agent 能够：

- 从企业知识和规则中理解任务及约束；
- 识别、校验并调用已注册的数字工具；
- 复用已审批的固定 Workflow；
- 对未知问题进行受控探索，形成可审查的图谱和执行轨迹；
- 将验证过的探索结果沉淀为可复用的知识、规则、工具连接或 Workflow；
- 对数字系统中的实际状态变化取得独立、可追溯的反馈，而不是把模型文本当作动作成功证据。

当前“LLM-Wiki 负责知识层、规则层、工具注册层、Workflow 层存储，以及未知可探索图谱和已知固定工作流”的职责设想尚未拆分为清晰的资产类型、权威来源、生命周期和运行时接口，容易造成知识、规则、工具和可执行流程混存，进而带来版本漂移、越权调用、错误固化和状态失真的风险。

## Proposed outcome
形成一套经过明确边界定义的数字世界 VLA Agent 架构设计，使项目能够在企业数字系统、API、数据库和软件界面等数字环境中，以多模态/语言输入理解任务，以受治理的数字动作执行任务，并以外部系统状态验证结果。

成功结果应包括：

- 明确区分知识、规则、工具契约、Workflow、探索图谱、固定流程、Context 和执行证据的职责；
- 定义 LLM-Wiki 作为逻辑资产入口时的引用、版本、审批、失效和回滚机制；
- 保留现有“命中固定流程直接复用、未命中受控探索、验证后人工审批固化”的双路径与双闭环；
- 明确视觉/语言输入到数字动作的边界，以及数字动作的前置条件、权限、幂等、回执和独立验证要求；
- 明确哪些能力属于架构设计，哪些能力需要后续运行时、连接器、浏览器自动化、多模态模型或外部系统补充；
- 以一个可验证的企业数字场景作为最小落地范围，首期输出建议、查询或受控操作，不默认开放高风险自动写入。

## Affected users and systems
- 业务用户：通过自然语言或截图/界面状态提交查询、分析和操作任务。
- Agent 运行时：任务理解、上下文组装、规划、工具选择、Workflow 执行、验证和降级。
- LLM-Wiki：知识、规则、能力资产索引、探索结果和固定流程的逻辑入口。
- Ontology 与 Context：数字世界对象、关系、状态、约束和来源的统一语义层。
- Connector Runtime：ERP、MES、WMS、数据库、API、文件系统和数字界面的受治理访问层。
- LangGraph Workflow：已审批固定流程的编排和断点恢复执行层。
- 治理与审计系统：权限、版本、审批、血缘、执行证据、评估和回滚。
- 外部数字系统：提供实际状态和动作结果的业务系统；其状态是结果验证的权威来源。

## Constraints
- 当前仓库是架构设计文档仓，不新增运行时代码；主架构文档的修改必须在意图批准和规范批准后进行，并遵循版本升级与增量说明约定。
- 不把 LLM-Wiki 的自然语言内容直接当作可执行权限、工具实现或动作成功证据；可执行资产必须经过契约校验、版本绑定和发布门禁。
- 不把出现在屏幕上的文本、模型总结或工具 `accepted` 状态直接等同于数字业务动作已成功；结果必须按外部系统状态或独立证据验证。
- 对探索性行为实行范围、权限、预算、超时、敏感数据和副作用控制；未知结果不得盲目重试或自动固化。
- 固定 Workflow、规则、工具契约和本体映射必须可追溯、可审批、可回滚，并声明适用域和版本依赖。
- 首期不预设具体多模态模型、浏览器自动化框架、数字系统协议、数据库、向量库或图数据库；选型需基于目标场景和现有连接器能力确认。
- 与实体机器人/物理世界控制分离：本意图只覆盖数字世界动作；物理感知、定位、运动规划、控制和硬件安全不属于首期范围。

## Open questions
1. “数字世界 VLA”是否明确包含视觉输入（截图、视频帧、界面 DOM/可访问性树），还是先限定为语言/结构化事件输入到数字工具动作？
2. 数字动作首期覆盖哪些环境：ERP/MES/WMS API，数据库查询，文件处理，浏览器界面操作，还是其中一个具体场景？首个可验证业务任务是什么？
3. LLM-Wiki 的定位是逻辑资产注册与编译入口，还是知识、规则、Workflow、图谱等全部内容的唯一物理存储？各类资产是否允许落在独立仓库/数据库后由 Wiki 引用？
4. “未知的可探索图谱”具体要记录什么：实体/关系候选、任务分解、工具发现、执行轨迹、界面状态，还是这些对象的组合？探索结果的确认者是谁？
5. “已知固定工作流”是否继续以 LangGraph 定义为运行时权威，LLM-Wiki 仅保存索引、元数据和版本引用？
6. 规则层是否包含仅供推理的业务规则、强制执行的策略规则和安全策略？三者是否需要不同的引擎、审批和失败处理？
7. 首期是否允许有副作用的写入动作？如果允许，哪些动作必须人工确认，哪些动作可以在满足条件时自动执行？
8. 目标运行形态是本地单机验证、企业内网服务，还是多租户平台？对数据隔离、审计留存、延迟和可用性有什么硬指标？
9. 是否已有可复用的 LLM-Wiki、LangGraph、Connector Runtime 或本地模型实现；若有，其接口、版本和可信边界是什么？
10. 该方向是否需要与前一轮机器人具身智能设计保持同一套 Ontology/Context/TaskRun 契约，还是作为仅面向数字环境的独立 profile？
